Spec: [spec.md](spec.md). Each task says what "done" means. The phases run in order. Tasks within a phase can run in parallel where noted.

## Phase 1: Version check and matrix

### T1. `find-tmf-api-versions` skill
- `scripts/api_versions.py`:
  - lists the `tmforum-apis` repositories through the GitHub API;
  - matches the v4 `*.swagger.json` / `*.swagger.yaml` files and the v5 `*.oas.yaml` files, and gets each minor version, raw URL and commit SHA;
  - applies the spec §2 exclusions;
  - writes `api-versions.json`, with a one-day cache.
- Takes a TMF id, a TMFC code (reading core exposed APIs from the component spec YAML) or a chart folder (reading them from `helm template`).
- `SKILL.md` covers when to use it and how to read the output.
- Unit tests with recorded API responses.
- **Done:** gives the spec §2 table for this repository's charts. It reports that nothing more qualifies on Product Catalog, and why.

### T2. Matrix flattener and classifier
- Generalise `flatten_tmf620.py` into `flatten.py`. It takes the resource list from the paths that both specifications define.
- `classify.py` sorts each difference into the rule kinds in spec §4.2 and writes `matrix.json`, with a schema for it in `references/matrix-schema.md`.
- `references/rule-kinds.md` gives one TMF620 example per kind, from the #87 matrix.
- **Done:** on TMF620 v4.0.0 → v5.0.0, `matrix.json` contains every row of the #87 matrix (G1–G10, R1–R2, K1–K2, S1–S9, and the O and P rows), each with the same rule kind.

### T3. Common-model patterns and spec defect checks
- Recognise the v5 common-model patterns by schema name: RelatedParty, characteristics, attachments, `Extensible` / `@type`, and ref `version`. Each maps to a shared rule id, so the same code is used for every API.
- Spec defect checks:
  - subtypes missing from a discriminator `mapping`;
  - `oneOf` branches that aren't exclusive;
  - `required` attributes not defined in the schema.
- Each defect found gets an upstream issue draft from a template.
- **Done:** finds both TMF620 v5.0.0 defects that #87 found. Run on TMF632, TMF637 and TMF638, it lists their defects, if any, and the rows it doesn't recognise.

### T4. Matrix markdown and the `build-tmf-compatibility-matrix` skill
- Template for `compatibility-matrix.md`, in the #87 layout (sources with SHAs, legend, rows by group, error and warning codes).
- `SKILL.md` covers the inputs, running the scripts, and the **review gate**: show the refuse rows and the hand-written rows, and stop.
- Evals in the `skills/skill-creator` format.
- **Done:** produces a TMF620 matrix that matches #87 except in wording. A TMF632 matrix is drafted, ready for the pilot's review.

## Phase 2: Implementation skill

### T5. Compat core template
- Copy `shared/tmf620-compat/lib/*` into `templates/compat-core/`, and take out everything specific to TMF620:
  - resource names;
  - the `TMF620` code prefix;
  - the storage schema id;
  - the `Catalog` → `ProductCatalog` rename, which becomes a G1 rule from `matrix.json`.
- Keep the shape generator's check that ignores line endings.
- Parameters come from one `compat.config.json`: API id, versions, resources, collections and component name.
- **Done:** with a TMF620 config, the #87 unit tests pass against the template (54 tests).

### T6. Rule generator and shared rule library
- `scripts/generate_rules.py` turns `matrix.json` into `rules/*.js`, one module per resource, for the mechanical rule kinds.
- `references/common-rules/` holds the RelatedParty, characteristic-value, attachment and ref rules, moved out of `translate.js` and `charValue.js`.
- For hand-written rows, it generates a stub that throws, plus a failing test named after the row.
- It also generates one unit test per matrix row, with fixtures from the published samples where there are any.
- **Done:** for TMF620, generated rules plus the common rules pass the #87 translate, patch and migrate tests, and no stubs are left.

### T7. v4 integration template
- Generalise the storage layer (`tmf620Storage.js`), the startup migration with quarantine, and the idempotent `/hub` dedupe.
- `references/v4-integration.md` covers wiring them into a v4 service generated by `create-oda-component`: where the calls go in `operations.js`, `listResource.js` and `retrieveResource.js`, and the warning header.
- **Done:** applied to a fresh copy of Product Catalog's 1.4.6 v4 service, it gives a service that passes the #87 v4 unit tests (16).

### T8. v5 service template
- Generalise `productCatalogV5Microservice`:
  - Express with `express-openapi-validator` on the unchanged OAS;
  - generic CRUD handlers driven by the paths in the OAS;
  - filters, paging, `fields`, and merge patch and JSON Patch;
  - converting v4-format documents on read;
  - a value check for polymorphic subtypes;
  - the API root, the health check and a Dockerfile.
- **Done:** with the TMF620 OAS, the #87 v5 unit tests pass (25). With the TMF632 v5 OAS, it starts and answers CRUD in a smoke test.

### T9. Metrics, chart and docs templates
- The compatibility endpoint and counter for the metrics microservice.
- Chart changes:
  - the v5 deployment and service;
  - the second `specification[]` entry;
  - `component.tmfxxxv5.enabled`;
  - the `TMFxxx_V4_API_URL` env vars.
- The README sections ("TMFxxx v4 and v5", migration, upgrade notes, configuration rows), and a changelog line.
- `dockerbuild-config.yaml` entries, with every changed image's version bumped.
- The diagram wrapper that draws one row per `specification[]` entry and copies a single entry's fields up.
- `references/chart-changes.md` covers the **rename-release rule** (spec §3, rule 7) and how to tell when a rename release is needed.
- **Done:** applied to Product Catalog chart 1.4.6, the rendered chart matches 1.5.0 from #88, except for image tags and wording.

### T10. `implement-dual-version-api` skill
- `SKILL.md` ties T5 to T9 together, for both retrofit and greenfield modes.
- It stops before a rename release, and stops on any hand-written stub.
- Evals.
- **Done:** run end to end on TMF620 v4.0.0 → v5.0.0 in a scratch copy of Product Catalog 1.4.6. The result passes all the #87 unit tests (spec §6 golden test, part 1).
